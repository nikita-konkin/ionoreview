# Дообучение визуальной модели для ионограмм

Подготовлен экспериментальный контур QLoRA для **Qwen/Qwen3.5-2B**. Это отдельная
визуальная модель в формате Hugging Face; существующий `fast` в `N:\local_llm_helper`
— Qwen3.5-9B GGUF — остаётся без изменений. Его GGUF-файл не используется как
обучаемый checkpoint, а адаптер 2B нельзя подставлять в модель 9B.

Код и учебные данные находятся на N. Окружение, веса и результаты вынесены на C,
где достаточно места:

- Python: `%USERPROFILE%\.t3\training-envs\ionoreview\Scripts\python.exe`;
- веса: `%USERPROFILE%\.cache\ionoreview-training\hub`;
- адаптеры, checkpoints, задания: `%USERPROFILE%\.cache\ionoreview-training\runs`;
- конфигурация: `training/config.json`;
- активный датасет: путь в `training/data/latest.json`;
- диагностика: `training/reports/doctor.json`, `real_step_smoke.json`.

Модель закреплена на revision `15852e8c16360a2fea060d615a32b45270f8a8fc`.
Обучающие изображения и аннотации не отправляются в Hugging Face: оттуда только
скачиваются публичные веса. `trust_remote_code` не включается.

## Готовность и запуск

На этой машине окружение и веса уже установлены. Для повторной установки:

```bat
Install-Training.cmd
Prepare-Training.cmd
```

Первый скрипт создаёт отдельный venv и устанавливает закреплённые зависимости.
Он использует установленный CUDA PyTorch; если его нет, ставит CUDA 12.8 wheels
в отдельное окружение. Основной Python и окружение local_llm_helper не обновляются.

`Prepare-Training.cmd` скачивает недостающие веса, собирает новый снимок только
**принятых** аннотаций и проверяет токенизацию. Пересборка с теми же входными
данными повторно использует снимок. Результаты эксперта не изменяются.

Полный пробный цикл на три эпохи:

```bat
Start-Finetune.cmd round001
```

Имя запуска должно быть новым: существующие адаптеры не перезаписываются.
Используется batch=1, accumulation=4, NF4, BF16, LoRA r=8, learning rate 1e-4,
gradient checkpointing. Vision encoder заморожен; обучаются LoRA-проекции текстового
декодера. Выбирается checkpoint с меньшей validation loss, итог — `runs/round001/adapter`.

На RTX 5080 проверен forward/backward/optimizer step с реальными весами и самым
длинным обучающим фрагментом: 3073 токена, пиковое выделение около 12.9 ГиБ.
Проверка CUDA NF4 и загрузка настоящих весов на CPU тоже прошли.
Проверен и сам Trainer: технический запуск `trainer-preflight` на один optimizer
step с validation и сохранением адаптера. Адаптер загрузился для генерации и
экспорта HF. Он предназначен для проверки цепочки, **не для рабочей разметки**;
полные три эпохи в этом запуске не выполнялись.
Перед обучением требуется 13.3 ГиБ свободной VRAM. Скрипт откажет при нехватке
памяти, не завершая чужие процессы и не выгружая LM Studio самостоятельно.
Применяется тот же `gpu.lease`, что у local_llm_helper: одновременные задания
помощника и обучения не занимают карту вместе.

На Windows используются корректные референсные PyTorch реализации линейного
attention/causal convolution; FLA/Triton-ускорение не установлено. Скорость будет
ниже варианта с оптимизированными Linux kernels. Объём памяти для новых, более
плотно размеченных данных нужно проверять снова.

## Что входит в датасет

На момент подготовки: **12 исходных ионограмм**, 145 полигонов. Разделение по
целым UTC-дням сохранено: **5 train / 2 validation / 5 test**. Фиксированная сетка
256×256 с перекрытием 64 даёт 90 / 36 / 90 фрагментов соответственно.
Это по-прежнему 12 независимых исходников, а не 216 независимых наблюдений.

Каждый пример содержит общий обзор для контекста, фрагмент в исходном разрешении,
границы частоты/дальности из NPZ и JSON полигонов только для фрагмента.
Сетка одинакова для подготовки и инференса и не выбирается по эталонным маскам.
Координаты ответов нормированы в 0…1000 по центрам крайних пикселей фрагмента.
Обучение не требует генерировать номера физических экземпляров: `group_id`
назначает эксперт при проверке, а исходные группы остаются в эталоне.

Loss считается только по ответу ассистента. Prompt, изображения и padding исключены.
Длинные ответы **не обрезаются молча**: `inspect` проверяет все примеры и останавливает
подготовку при превышении 4096 токенов. Тестовые изображения не поступают в optimizer
или few-shot контекст обучения. Веса и наборы закреплены revision/fingerprint.

В четырёх исходных полигонах обнаружены самопересечения. Только в учебной копии
они разделены `make_valid`; совпадение растрового заполнения с оригиналом — 1.0
для трёх и около 0.9992 для одного. Две части площадью меньше половины пикселя
после отсечения границей фрагмента пропущены. Это записано в `report.json`.
Ни один исходный JSON принятой разметки не менялся.

Проверен также полный цикл «эталон → нормированные полигоны фрагментов → маски
исходного размера». Macro IoU представления: около 0.982 / 0.941 / 0.960 для
train / validation / test. Это погрешность преобразования контуров и растеризации,
**не качество модели**; подробности — `training/reports/representation_fidelity.json`.

**Выводы о качестве пока делать рано.** В train всего один полигон `1E`;
validation содержит только `1E` и `3F`, test — без `1E`. Для `E`, `Es` и
`Interference` принятых примеров нет. `Signal` сохраняется как неопределённый
полезный сигнал. Нужны новые принятые ионограммы разных дней и мод, после чего
следует повторить `Prepare-Training.cmd`. Тест не используйте для выбора настроек.

## Проверка качества и предложения в редактор

Из корня проекта, PowerShell:

```powershell
$py = "$env:USERPROFILE\.t3\training-envs\ionoreview\Scripts\python.exe"
$runs = "$env:USERPROFILE\.cache\ionoreview-training\runs"
# Базовая модель и адаптер сравниваются на одной и той же validation части.
& $py -m ionoreview.finetune predict-set --split validation --out "$runs\baseline-val"
& $py -m ionoreview.finetune evaluate --split validation --predictions "$runs\baseline-val"
& $py -m ionoreview.finetune predict-set --split validation --adapter "$runs\round001\adapter" --out "$runs\round001-val"
& $py -m ionoreview.finetune evaluate --split validation --predictions "$runs\round001-val"
```

Оценка: семантические IoU/Dice по исходным полным изображениям, с объединением
перекрывающихся фрагментов. Пустые классы не повышают macro IoU. Невалидный JSON
считается ошибкой и пустым предсказанием; его доля указана отдельно. Неполная
папка предсказаний не оценивается. Это не instance AP и не доказательство физической
интерпретации мод. Все фактические ответы модели сохраняются для разбора.

Предложение для одной ионограммы:

```powershell
& $py -m ionoreview.finetune predict --pack chirp_h5_014 --case ИДЕНТИФИКАТОР_ИЗ_MANIFEST --adapter "$runs\round001\adapter" --out "$runs\review-example"
```

Команда создаёт `proposal.labelme.json`, не меняя `annotations`. Откройте тот же
случай в редакторе и используйте **Импорт разметки LabelMe…**. Полученные контуры
требуют проверки, исправления и объединения групп: перекрывающиеся фрагменты
могут дать пересекающиеся предложения. Автоматического принятия нет.
Если часть ответов невалидна, JSON помечается как неполный.

Для окончательной оценки после фиксации настроек замените `validation` на `test`.
Тестовые результаты не используйте для повторной подгонки этой же модели.

## MCP для изображений и обучения

Текущий `local_llm_helper` — текстовый помощник: PNG у него запрещены как binary.
Отдельный сервер `ionoreview.finetune.mcp_server` добавляет операции с изображениями,
используя общий GPU lease, без изменений исходного помощника.
Пример подключения: `training/mcp.example.json`. Укажите его сервер в настройках
своего MCP-клиента; этот файл не меняет глобальную конфигурацию клиента автоматически.

Инструменты:

- `training_dataset_status` — состав текущего снимка;
- `prepare_training_data`, `inspect_training_data` — подготовка и проверка;
- `start_finetune(run_name, max_steps=0)` — очередь обучения;
- `propose_ionogram(pack, case_id, run_name)` — очередь предразметки;
- `training_job_status(job_id)` — состояние, результат и пути к журналу.

Пустой `run_name` у предразметки означает именно базовую модель 2B. При указанном
имени адаптер должен существовать; скрытой подмены на другую модель нет. Тяжёлые
операции выполняются отдельными процессами, MCP возвращает пути/счётчики, а не
картинки или весь текст генерации. Работа MCP проверяется через stdio.

## Экспорт и воспроизводимость

Адаптер работает напрямую через MCP/CLI. Для независимой HF-копии с vision encoder:

```powershell
& $py -m ionoreview.finetune merge --adapter "$runs\round001\adapter" --out "$runs\round001-merged-hf"
```

Это HF-модель, не GGUF. Для LM Studio нужна отдельная корректная конвертация
вместе с визуальным projector; существующий GGUF 9B не является заменой базы 2B.
Веса/адаптеры/датасеты не попадают в Git и сборку Windows-редактора.

Тесты подготовки: `& $py -m pytest tests/test_finetune.py -q`.
Исходники API: [Qwen3.5 Transformers](https://huggingface.co/docs/transformers/model_doc/qwen3_5),
[PEFT LoRA](https://huggingface.co/docs/peft/developer_guides/lora),
[bitsandbytes Windows/CUDA](https://huggingface.co/docs/bitsandbytes/v0.50.2/en/installation).
